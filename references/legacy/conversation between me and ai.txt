English Learning App — Project Description & A1 Build Plan
1. Product Vision
We are building a serious English learning application for Arabic-speaking learners.

This is not a Duolingo-style casual game.
The app is designed for learners who genuinely want to understand, practice, and retain English.

The core idea is:

The learner should not just “see English.”
They should understand it, use it, explain it, and review it.

The app combines:

structured curriculum

Arabic explanations

English examples

vocabulary

grammar patterns

audio

video lessons

guided practice

AI interaction

teach-back learning

spaced review

The goal is to build a full English course, starting with A1, based on recognized curriculum foundations, not random content.

2. Curriculum Foundation
The curriculum should be built using four main sources:

1. CEFR Companion Volume
Used for level validation and broad descriptors.
The CEFR Companion Volume updates and extends the older CEFR framework, adding richer descriptors, Pre-A1, mediation, online interaction, and more detail at A1 and C levels. 


2. Pearson GSE Adult Learning Objectives
Used as the main source for micro-objectives / can-do goals.
GSE is more granular than CEFR and defines what learners can do across speaking, listening, reading, and writing. 


3. English Grammar Profile
Used for grammar and pattern validation by level.

4. Oxford 3000 / 5000
Used as the vocabulary pool for each level.

The curriculum logic should be:

GSE Objective
→ CEFR Level Validation
→ Grammar Profile Pattern
→ Oxford Vocabulary
→ Ability Lesson
→ Practice
→ Review
3. Final Curriculum Structure
The app should follow this hierarchy:

Level
→ Unit
→ Ability
→ Lesson
Important decision:

Each Ability is one full Lesson.

So we are not creating tiny 5-minute daily games.
Each lesson should feel like a proper learning session.

Expected lesson length:

25–40 minutes
The app is for serious learners.

4. A1 Curriculum Structure
A1 should be divided into 7 units.

A1 Units
Unit 1 — Identity
Learner can introduce themselves and exchange basic personal information.

Examples:

Unit 2 — People & Relationships

Unit 4 — Places & Movement
Learner can talk about places and movement.

Learner can handle simple needs.

Examples:

buying things

asking price

ordering food/drinks

cafe

restaurant

supermarket

want / need / can

Unit 6 — Simple Communication
Learner can communicate in very simple ways.

Examples:

greetings

short questions

simple replies

polite phrases

basic messages

Unit 7 — Reading, Signs & Forms
Learner can understand and complete simple written information.

Examples:

signs

menus

short notices

forms

name / address / phone / email

5. Lesson Philosophy
Each lesson is based on one ability.

Example:

Ability:
Introduce yourself

Lesson:
The learner should be able to say their name, where they are from, and ask another person simple identity questions.
The lesson should not be just vocabulary.

Each lesson includes:

😂 Okay, alien verdict after landing on Earth:

The core plan is very strong. But I would not start building the full app yet.

The product idea is right. The curriculum direction is right. The risky part is that we have started treating some hypotheses as final decisions.

My honest evaluation:

Product vision: 9/10

Learning philosophy: 9/10

Curriculum foundation: 8.5/10

Current build readiness: about 6/10

Not because the idea is weak. Because several important things still need validation before code.

What I would lock now
These decisions are strong:

1. Serious learners, not casual streak users
Keep this.

The product is not:

“Open the app for five minutes and keep your streak.”

It is:

“Sit down, understand one useful ability deeply, practice it, use it, explain it, and review it.”

That is a real position in the market.

2. Native-language explanation
Keep this as a core advantage.

A beginner often needs someone to explain:

what the English means

why the sentence works

what Arabic speakers commonly misunderstand

what the difference is between similar forms

This does not mean translating everything forever. It means using Arabic strategically to accelerate understanding.

3. Curriculum based on external objectives
Correct.

GSE should help define what the learner should be able to do, while CEFR validates the broader proficiency level. GSE is intentionally more granular and covers speaking, listening, reading, and writing. 


4. Ability = one lesson
I would keep this rule.

But I would define it more precisely:

One lesson should have one clear, measurable learner outcome.

For example:

By the end of this lesson, the learner can introduce themselves with their name, country, city, and role, and answer the same questions from another person.

That can be one meaningful 30-minute lesson.

The word Ability is our product layer. It does not have to equal exactly one GSE sentence.

One lesson may use:

several related GSE objectives

several CEFR descriptors

multiple grammar patterns

a small vocabulary set

The important thing is that they all support one coherent real-life outcome.

5. Explain → Practice → Use → Teach → Review
Keep this.

Especially:

personal use

AI conversation

teach-back

review

Those are probably more valuable than adding fifty types of multiple-choice questions.

What I would not lock yet
1. The seven A1 units
The seven units look sensible:

Identity

People & Relationships

Everyday Life

Places & Movement

Needs & Transactions

Simple Communication

Reading, Signs & Forms

But they are currently our proposed organization, not a validated A1 map.

Before treating them as final, we need to extract all relevant A1 objectives and check:

Can every A1 objective fit naturally into one of these units?

Also:

Are listening, speaking, reading, and writing represented well?

The CEFR itself is a flexible framework, not a ready-made course table of contents. It expects curriculum designers to select, adapt, and organize descriptors for their context. 


So creating our own units is correct.

But they need a coverage audit first.

2. The number of abilities inside each unit
We previously said:

Unit 1 may have six or seven abilities.

That is still a draft.

We should not decide:

Identity
→ exactly 7 abilities
before reading and clustering the objectives.

The correct direction is:

A1 source objectives
→ group related objectives
→ create lesson-sized abilities
→ organize them into units
Not:

Invent 7 units
→ invent 7 abilities per unit
→ force the references into them
That difference is important.

3. The exact lesson flow
This is currently a strong hypothesis:

Warm-up
→ Video
→ Toolkit
→ Practice
→ Personal Use
→ AI Challenge
→ Teach-back
→ Review
I like it.

But I would not make it a rigid law before testing one complete lesson.

Maybe users prefer:

Warm-up
→ Short situation
→ Video explanation
→ Practice
Maybe the toolkit should appear during the video.

Maybe a 15-minute video feels excellent.

Maybe it feels too passive.

We do not know yet.

So the flow should be treated as:

Version 1 lesson hypothesis

not:

final architecture for all A1 lessons

4. A required long teach-back after every lesson
Teach-back may become your strongest differentiator.

But it can also become repetitive.

Imagine lesson 18:

“Now explain the lesson again.”

The learner may say:

“يا عم أنا فهمت 😂”

I would initially test:

a short teach-back in every lesson

a deeper teach-back at the end of a unit

Example of a short lesson teach-back:

“Explain in your own words why we say ‘I am from Egypt,’ not ‘I from Egypt.’”

That may take one minute.

Then the unit-end AI session can be deeper.

5. Every lesson must be 30–40 minutes
The serious-learning philosophy is correct.

But I would avoid forcing every ability into the same duration.

Some may naturally take:

20 minutes

30 minutes

45 minutes

The important thing is not duration.

The important thing is:

Did the learner gain the ability?

A serious course does not have to make every lesson long.

It has to make every lesson valuable.

The biggest missing part: mastery
We designed the learning experience, but we have not yet properly defined:

What proves that the learner learned the ability?

Watching the video is not mastery.

Finishing exercises is not necessarily mastery.

Getting 8/10 multiple-choice questions is not necessarily mastery.

For every lesson, we need a small success rubric.

Example:

Lesson: Introduce Yourself
The learner should be able to:

Understand basic personal questions.

State their name, country, city, and role.

Ask another person similar questions.

Respond without copying a complete model.

Correct or explain one important pattern.

Then the lesson status can be:

Not started
→ Learning
→ Practiced
→ Demonstrated
→ Needs review
→ Retained
This mastery layer is more important than adding more screen types.

The corrected plan before building
I would now organize the project into these medium tasks:

Phase 1 — Lock the learning model
Define:

who the learner is

what “serious learning” means

lesson philosophy

role of Arabic

role of video

role of AI

role of teach-back

what mastery means

Output:

Product Learning Principles document

Phase 2 — Build the complete A1 curriculum map
Do the real curriculum work:

All A1 objectives
→ categorize by skill
→ group into meaningful units
→ create lesson-sized abilities
→ check complete coverage
Output:

A1
→ Final Units
→ Final Abilities/Lessons
→ Source mapping
Only after this should we say:

A1 has exactly X units and Y lessons.

Phase 3 — Normalize lesson size
Check every ability:

Is it too small?

Is it too large?

Can it produce one meaningful learning session?

Does it have one measurable outcome?

Merge tiny abilities.

Split huge abilities.

Output:

Final A1 lesson list

Phase 4 — Design one “gold lesson”
Not seven units.

Not full A1.

One exceptional lesson.

Probably:

Introduce Yourself

Create the entire experience:

warm-up

video script

doodle plan

toolkit

vocabulary

patterns

examples

audio

exercises

personal use

AI challenge

teach-back

mastery evaluation

review

This lesson becomes the reference for the entire product.

Phase 5 — Prototype before engineering
Build the lesson as a clickable prototype.

It can use:

Figma

fake AI responses

placeholder audio

temporary video

no real backend

Then let real Arabic-speaking beginners use it.

Observe:

Did they understand?

Were they bored during the video?

Did the Arabic explanation help?

Did they know what to do next?

Were the exercises too easy?

Did teach-back improve understanding?

Did the lesson feel worth 30 minutes?

Phase 6 — Lock the lesson system
After testing, finalize:

lesson flow
screen types
content structure
exercise types
AI behavior
mastery rules
review logic
Now we have evidence.

Phase 7 — Design the technical architecture
Only now define:

database

lesson JSON

content CMS

video integration

audio storage

exercise engine

AI sessions

progress system

review system

The database should follow the learning experience.

The learning experience should not be forced into an early database design.

Phase 8 — Build Unit 1
Build the first complete unit.

Not the full A1 level.

Test:

lesson progression

review across lessons

unit completion

AI memory/context

learner motivation over several sessions

Phase 9 — Pilot Unit 1
Give it to real learners for one or two weeks.

Then improve:

lesson duration

amount of Arabic

video style

exercise difficulty

teach-back frequency

review timing

Phase 10 — Produce full A1
Only then:

generate lessons

write videos

create assets

review content

publish all units

My strongest recommendation
Do not start by:

building the complete database

generating all A1 vocabulary

producing all videos

writing all lessons

building every exercise type

Start with:

A1 curriculum audit
→ one gold lesson
→ learner testing
→ Unit 1
→ full A1
That will save months.

The vision is not the problem.

The vision is actually unusually strong.

The danger is building a large, beautiful system around assumptions we could test with one lesson first.
